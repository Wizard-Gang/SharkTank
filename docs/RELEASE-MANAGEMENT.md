# Release management

A release is an annotated semantic tag `vX.Y.Z` on an accepted `main` commit. A controlled release change advances the root `package.json` and `package-lock.json` version authority together. After merged-main CI succeeds, the Release Tag workflow compares that exact commit with its parent: unchanged versions are a no-op; a valid semantic version increase creates one annotated tag on the accepted commit; an existing matching annotated tag is idempotent; any lightweight or conflicting existing tag fails closed and is never moved or recreated. Only the latest supported release receives fixes.

Release history is authoritative in annotated `v*` tags and GitHub Releases. Repository Markdown does not mirror per-version release history. GitHub Actions is the authority for CI and release-workflow run history.

The Release Tag workflow has no manual or branch-push trigger of its own: it observes only completed `CI` workflow runs and acts only when the successful source run was a `push` to `main`, checking out that exact accepted SHA with full history. Its guarded repository command refuses workstation context and binds the workflow identity before any tag mutation. The release workflow then installs the lockfile, runs `npm run check` and the separate live `npm run audit:dependencies` gate, and verifies that the tag event identity is an annotated semantic tag resolving to the checked-out `HEAD` and matching the root `package.json` version before publication. Publication is create-or-verify: an absent Release is created once with exact-tag verification and generated notes, while a matching existing non-draft/non-prerelease Release is accepted without editing it. A mismatched tag/title, draft, prerelease, lookup failure other than a confirmed 404, or conflicting follow-up state fails closed. Only after that publication succeeds can the Release workflow call `.github/workflows/deploy.yml` with the same event tag. The reusable deploy workflow has no branch or manual trigger, revalidates the caller tag against the event and tagged `HEAD`, and owns the protected `production` environment. Production deployment remains optional and has three gates: repository variable `PRODUCTION_DEPLOY_ENABLED=true`, the protected `production` environment, and required Cloudflare secrets. The deployment script independently refuses real deployment unless it is running in GitHub Actions for the exact SharkTank Release workflow semantic-tag context, the annotated tag/package identity resolves at `HEAD`, and the protected-environment Cloudflare credentials are present. Real mode never loads local `.env`; only the explicit dry-run may do so.

After deployment, the production job confirms the uploaded version through authenticated Cloudflare deployment evidence and requires it to serve 100% of traffic. Public `/version.json` and evidence checks run when the edge permits them; a Cloudflare managed challenge is reported only after provider-side deployment proof succeeds.

Published `v*` release tags are protected by the repository's active tag ruleset against update and deletion. Never move or recreate a published release tag. Correct defects forward with a new patch release. Cloudflare/provider evidence is authoritative for deployment/runtime provider state; do not maintain a checked-in deployment ledger.
